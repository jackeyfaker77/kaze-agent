## 1. 产品目标与交付边界

目标体验：

> 用户在桌面或 Telegram 与 Kaze 交流；Kaze 保留完整交互历史，理解长期偏好，能够召回相关经历，在合适时机主动提醒。发生中断后，已提交事实可恢复，未知结果可见，恢复不会盲目重复外部操作。

目标架构：

```text
Runtime Host：运行所有权、启停、后台工作者、健康与收尾
    │
    ├── Runtime Event Log：agent 交互语义事实
    │       ├── UI 会话投影
    │       ├── 执行状态与恢复计划
    │       └── 模型历史与已记录请求的重建
    │
    ├── Markdown：长期画像与明确维护的用户事实
    ├── Akasha：历史关联检索、学习图与兴趣能力
    ├── 主动链：判断、打扰控制、投递与受控恢复
    └── 独立领域：待办、调度、收发队列、配置
```

模型历史由交互事实投影；实际新请求还需结合系统提示词、当前输入、工具定义和取得的记忆材料组装，并保存其可复核记录。
“一份事实、多种投影”限定 agent 交互语义，不要求所有领域全部改为事件溯源。

| 项目 | 本轮路线约束 |
|---|---|
| 入口 | 保留桌面与 Telegram、本地与远程模式 |
| 主动轮询 | 常规轮询保持 300 秒；测试时钟不改变生产配置 |
| 配置 | 当前配置暂不修改；Akasha 正式切换另行安排 |
| 部署 | 暂缓服务器常驻，不作为个人使用首版条件 |
| 运行时间 | 本地 Host 未运行时，不承诺 Telegram 收发和主动提醒在线 |
| 交付判断 | 区分代码实现、回归通过、真机验收与部署证明 |

“能恢复运行”与“完成用户目标”分别验收。执行终态不能只凭模型一句“完成了”裁决。

## 3. 权威边界与状态所有权

| 领域 | 权威来源／所有者 | 派生内容与边界 |
|---|---|---|
| Agent 交互语义 | Runtime Event Log | UI 对话、执行状态、模型历史由事实投影 |
| 实际模型请求 | 已提交的请求记录及其输入材料 | 历史请求可准确重建；新尝试可使用当前配置，但记录新输入 |
| 执行资格 | 原子 claim、唯一约束及执行所有权 | 日志重放不能自行获得执行资格 |
| 后台记忆任务 | 原对话事实中的任务意图；任务存储拥有领取与处理状态 | 稳定关联原事实，不维护第二份对话真相 |
| Markdown 长期画像 | 画像维护模块 | 用户直接编辑与系统更新明确版本、来源及冲突规则 |
| Akasha | 历史事实、固定向量及必要的学习记录 | 图和索引为派生结果；重建不重新猜测历史输入 |
| 待办与调度 | 各自领域存储 | 通过稳定 ID 关联执行和提醒，保留独立权威 |
| Telegram 收发 | 持久 Inbox／Outbox | 队列拥有收发状态；执行日志拥有 agent 处理语义 |
| 生命周期 | Runtime Host | 启停、工作者所有权、健康及收尾；进程重启由外部启动器负责 |

跨存储提交采用两种方式：

1. 同一事务域内，原子提交事实与关联状态。
2. 跨事务域，先持久化意图，再按稳定身份处理并保存回执；重启扫描补齐。

同一事实只能有一个裁决者。UI、队列和执行状态可以不同，但必须解释各自含义，不能各自裁决消息是否发送成功。
若人工核对无法取得外部服务回执，人工结论应作为有来源的新记录，不伪造成原始成功回执。

## 4. 所有阶段必须保持的不变量

1. 重放和重建默认只读事实，不调用模型、工具或发送接口。
2. 已提交的模型结果直接复用，不为恢复重新生成。
3. 外部请求已发出而结果未持久化时保留未知状态；没有可靠核验或幂等协议，不自动重试。
4. 同一恢复边界只有一个执行者；重复点击、重连、双客户端竞争不能产生多个尝试。
5. 更新投影不能改变已提交的原始事实。
6. 历史请求重建不依赖当前提示词、技能和配置；真正的新调用明确记录新环境。
7. 旧历史缺少恢复证据时可以查看，但不能伪造为可安全续跑。
8. 后台任务均有来源、状态、失败原因和生命周期所有者。
9. 删除、更正、停止学习、归档分别定义效果；不能用一个布尔开关混代。
10. 不承诺外部服务端到端 exactly-once；用本地去重、已提交回执及未知结果阻塞控制风险。

## 5. Phase A：完成当前后台记忆可靠性

状态：限定范围已完成、已合并并验收（PR #29，`d6db2e7`）。

已验收范围仅为失效主题抽取、候选核对和隐式长期记忆。Markdown 历史归档、近期摘要及其 consolidation 回调不包含在 PR #29 的验收中；本轮独立补齐的状态见下文。Akasha 可靠恢复也不在本阶段内。

证据：[实现与崩溃矩阵](durable-memory-tasks-v1.md)。GitHub CI 后端 2178 项通过，桌面检查全部通过；包含 12 个真实进程崩溃边界。本机合并后重启验收确认原有 288 条消息不变，本地／Telegram 各新增一轮正常对话，后台任务各完成一次，旧任务未重跑，配置哈希不变。自动化远程验收与真实 Telegram 验收分别记录，不混同为服务器部署证明。

目的：修复目前实际使用的 memory2 链路，形成可独立交付的可靠基线。

### 实施范围

- 将后台任务意图与原对话事实稳定关联。
- 持久保存任务领取、步骤结果、失败和完成状态。
- 复用已提交的模型输出。
- 记忆新增、强化、合并和废弃具有稳定操作身份。
- 写入与操作回执保持原子性，或提供可证明的恢复规则。
- Runtime Host 管理工作者启停和恢复扫描。
- 对结果未知的模型请求明确保守策略，不把所有异常统一当成可重试。

建议按以下逻辑单元评审；若主任务已经形成一个边界清楚的 PR，不为形式重新拆分：

| 单元 | 内容 |
|---|---|
| A1 | 任务持久化、来源关联与领取机制 |
| A2 | 模型结果复用、记忆操作幂等与失败可见性 |
| A3 | 真实进程崩溃、并发恢复及历史兼容验收 |

### 验收 Gate A

- [x] 对话已提交、工作者未启动时崩溃，任务仍能被发现。
- [x] 模型结果提交后崩溃，恢复时模型调用次数不增加。
- [x] 记忆写入后、任务完成前崩溃，不重复强化或废弃。
- [x] 重复恢复得到相同业务结果。
- [x] 结果未知与可安全重试可区分，失败不会被静默标成完成。
- [x] 本地和远程均走正式生产链路。

阶段出口：当前记忆链路可验收。不能据此宣布 Akasha 具有相同保障。

## 6. Phase B：主动链的受控恢复

状态：PR #30–31 已合并并完成生产重启验收。[恢复契约、适配边界与证明矩阵](proactive-recovery-v1.md)。适配 Wake 单事件提醒／Context；未知结果、旧历史材料不足、任意 Drift 中间工具点及缺少收尾协议的插件激活继续阻塞。整包冷备份及隔离恢复演练已在本轮完成，发布材料见[基础版候选验收](../reliable-baseline-release.zh-CN.md)；恢复副本不自动接管线上业务。

验收证据：PR #31 CI 后端 2211 项、桌面 225 项、打包 5 项通过；合并后重启核对既有 295 条消息未丢失或修改，本地及 Telegram 各一轮真实对话正常，收发各一次，配置哈希未变。隔离恢复复测 26 项通过，ACK 明确失败、超时及未知结果保留待核对，重启和重复确认不重复调用模型、发送或 ACK。生产未注入 ACK 故障，隔离证据与真实收发证据分别记录。

已有事件化与发送去重作为基础，本阶段补齐未收尾任务的恢复，不重写整个主动算法。

| 中断位置 | 恢复原则 |
|---|---|
| 尚未开始判断 | 按原任务身份重新检查资格 |
| 判断结果已提交 | 复用判断结果，不重新调用模型 |
| 投递意图已提交、尚未发送 | 由同一 Outbox 身份继续处理 |
| 成功发送回执已提交 | 只补齐后续状态，不再发送 |
| 请求可能已发送、结果未知 | 标记待核对，不自动补发 |
| 提醒过期、待办取消或用户状态改变 | 记录取消或阻塞原因，不机械补投递 |

### 实施范围

- 区分历史判断结果与现在是否仍允许执行。
- 恢复时重新检查待办版本、有效期、停止状态和打扰条件。
- 重验证失败不偷偷启动新一轮模型判断。
- 提醒执行、待办／候选、判断结果与 Outbox 保持稳定关联。
- 用户明确停止后，不因重启再次恢复发送。
- 新的恢复入口复用只读计划、确认与竞争领取规则；自动收尾仅覆盖明确无新外部副作用的步骤。

### 验收 Gate B

- [x] 已完成判断不重复调用模型（本轮适配边界）。
- [x] 已确认发送不重复投递；部分分片回执不冒充整条完成。
- [x] 重启、重复点击、两个客户端竞争产生同一处理结果。
- [x] 过期提醒和取消待办不会被恢复流程重新激活。
- [x] 模型或发送结果未知时不会自动重放，人工重新排队不能绕过。
- [x] 生产轮询仍为 300 秒。

阶段出口：完成基础跨模块验收和备份恢复演练后，可交付“可靠基础版”。
继续使用当前记忆配置，明确 Akasha 尚未完成迁移。
若 Markdown 归档与摘要恢复仍延期，发布说明必须列出该限制，不得宣称全部后台记忆链已具备持久恢复。本阶段不顺带实现它。

## 7. Phase C：Akasha 契约与迁移准备

目的：先确定目标记忆架构，避免正式切换后才发现数据与行为不兼容。

| 层次 | 职责 |
|---|---|
| 会话上下文投影 | 当前对话、工具结果与执行连续性 |
| Markdown 画像 | 长期偏好、用户事实、明确要求长期记住的信息 |
| Akasha | 历史经历、相关片段与关联召回 |
| 主动链 | 消费画像与兴趣能力，决定是否打扰 |
| memory2 | 迁移期间继续服务；切换后保留归档与回退用途 |

### 实施范围

- 固定 Akasha 算法版本，审计 Kaze 现有实现与目标实现的差异。
- 明确在线学习与离线重建的共同输入、学习资格和状态转换。
- 定义会话、角色和渠道之间的共享范围，不默认跨身份或私聊／群聊混用。
- 审计 memory2 条目与 Markdown 的重叠和冲突。
- 无法可靠转换的结构化记忆保留归档，不伪造成原始对话。
- 生成 embedding 覆盖报告，明确缺失、模型不匹配和维度错误。
- 设计一致性备份、迁移标记和回退协议。
- 区分回退到切换前快照与保留切换后的新数据；后者需要明确补处理协议，不能只切回开关。

### 验收 Gate C

- [ ] 迁移在副本上完成，正式配置不变。
- [ ] 原始历史及其身份完整。
- [ ] 向量缺失明确阻止不完整重建被标记为成功。
- [ ] 长期画像迁移保留来源，可检查、可纠正。
- [ ] 明确迁移成本、外部 embedding 调用范围及回退限制。

阶段出口：可审查的迁移报告与切换方案。

## 8. Phase D：Akasha 生产接入与可靠恢复

这是实现目标产品记忆架构的核心阶段。

### 实施范围

- Akasha 消费已提交对话，使用持久消费进度和幂等学习身份。
- 复用持久任务的通用协议；memory2 专属事务实现不强行复用。
- 保存重建所需的向量、算法版本及必要的检索／学习输入。
- 在线与重建使用一致的学习规则。
- 将 Akasha 召回接入真实模型请求材料，记录实际使用的记忆来源。
- 接通主动链兴趣接口，分别验证对话召回与候选兴趣评分。
- 明确更正、删除、排除学习后的增量处理及重建行为。
- 原始事件仍存在时，逻辑遗忘／排除必须在重建中继续生效；物理删除另行定义处理范围。
- 副本验收后再安排正式切换，保留可执行的回退步骤。

### 验收 Gate D

- [ ] 对话提交、学习未完成时崩溃，重启能补齐。
- [ ] 重复消费不重复建边或强化。
- [ ] 固定输入与算法版本，重建得到相同的规范化逻辑状态。
- [ ] 旧经历可以召回，但不能覆盖已更正的当前偏好。
- [ ] 当前会话上下文不依赖 Akasha 是否可用。
- [ ] Akasha 不可用时明确报告记忆降级，不伪称没有相关记忆。
- [ ] 更正与遗忘在重启、重复消费和重建后仍生效。
- [ ] 切换后不会出现未经设计的 memory2／Akasha 双写和双检索。

阶段出口：目标记忆架构进入生产使用。

## 9. Phase E：整体验收与发布

用以下完整用户流程验证模块协作：

> 告诉 Kaze 一个偏好 → 新会话正确记得 → 找回当时相关经历 → 主动候选体现该偏好 → 不合适时保持安静 → 合适时通过 Telegram 送达一次 → 重启后历史与处理状态完整 → 更正偏好后不再按旧偏好行动。

### 发布证明矩阵

| 维度 | 必须验证 |
|---|---|
| 入口 | 本地桌面、远程桌面、Telegram |
| 历史 | 已有历史可读；投影删除后可重建 |
| 模型请求 | 清除缓存并改变当前配置，仍按原事件前缀重建历史请求 |
| 记忆 | 跨会话召回、画像更正、学习恢复、重复消费 |
| 主动行为 | 相关性、打扰抑制、过期取消、发送去重 |
| 故障 | 真实进程终止、网络错误、写入失败、竞争领取 |
| 运维 | 一致性备份、恢复演练、版本回退及明确限制 |

备份覆盖相互关联的事实、队列与领域存储。不能把运行中的多份数据库随意复制后称为一致性备份。
恢复旧备份后，也不能无条件发送其中的待处理消息：外部服务可能已收到这些消息，必须保留核对或隔离规则。

### 验收 Gate E

- [ ] 固定通过验收的提交与依赖版本。
- [ ] Gate A–D 及目标版跨模块矩阵有对应证据。
- [x] 完成一次实际备份恢复演练（2026-10-28：10 个数据库、91 文件；隔离恢复，不等同于恢复后在线接管）。
- [ ] 记录测试平台、故障注入点、外部调用计数和状态检查结果。
- [ ] 准备安装／启动说明、数据目录、配置要求、升级回退说明及已知限制。
- [ ] 区分基础版与目标版，不提前宣称尚未接入的能力。

阶段出口：交付“具有 Maka 式交互事实边界、Akasha 记忆与主动交互能力的 Kaze Personal Agent v1”。

## 10. 明确延后的能力

以下不阻塞目标版交付：

- 服务器或 Mac mini 的 24 小时常驻部署。
- Peer Mesh、多 Host 迁移与分布式执行。
- 通用文件系统 checkpoint 和任意工具自动恢复。
- 未知外部结果的全自动核验。
- memory2 与 Akasha 的长期双引擎融合。
- 复杂项目记忆图策略动态变更。
- 全项目事件溯源改造。
- 高级日志压缩和分层归档。

基础备份、删除语义和可观察性仍属于首版要求，不能随高级运维一起延后。

## 11. 依赖顺序与工程门槛

```text
A 回复后后台记忆可靠性（限定范围已验收，PR #29）
    ↓
B 主动链受控恢复（限定范围已验收，PR #30–31）
    ↓
可靠基础版：冷备份／隔离恢复（PR #32）＋Markdown 恢复（PR #33）＋shell／发送审计（PR #34）；固定 2ade483
    ↓
C Akasha 契约与副本迁移
    ↓
D Akasha 生产接入与可靠恢复
    ↓
E 全链路验收、备份恢复与发布
    ↓
目标版 Kaze v1
```

- 每个阶段满足验收条件后才能标记完成；代码已写、CI 通过、真机通过分别记录。
- Windows 是当前主要平台，崩溃恢复必须有 Windows 实际证据；其他平台结果不能代替。
- 测试必须经过生产入口、真实持久存储与实际领取机制；模型和外部渠道可在自动化测试中替换为计数边界。
- 自动化计数测试与真实 Telegram 收发验收分别记录，互不替代。
- 未提交或正在开发的工作不作为后续阶段已经成立的前提。
- 每阶段结束记录残余风险与下一阶段输入，不因接近发布而省略未知状态。
- 新需求进入后续阶段，避免在 Phase A/B 临时加入双引擎、服务器部署或通用自动续跑。
