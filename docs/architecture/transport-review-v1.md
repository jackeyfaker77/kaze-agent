# 收发队列关联查看与人工处置

基于 master `0f209ff`，保留本地 bridge 与远程 Runtime Host 的同一套业务入口。
没有修改生产配置、主动提醒 300 秒周期或进行服务器部署。

## 数据与关联

`queue.sqlite3` 继续拥有 Inbox/Outbox 的可变状态。本阶段没有把队列宣称为执行日志
的投影。新增 `transport_reviews` 为禁止更新、删除的处置审计；每条记录保存操作 ID、
请求版本位置、核对依据及操作前的任务状态、尝试数、分段物理状态、回执与关联执行。
人工结论不会变成平台成功回执，也不会覆写执行日志的原终态。

`jobs.revision` 在任务状态、尝试、期限和分段更新时递增；`review_closed` 独立表示
结束处置；`attempt_limit` 保存这次显式重试的累计尝试上限。升级只增加列和表，
保留原任务 ID、内容、账户、成功分段和回执。旧版本不能继续写这个工作区，否则会
忽略关闭标识而重新处理任务。

新发件意图和当前执行关联在同一个队列事务内落盘；独立投递执行也在物理派发前
关联。旧入站和普通回复按已有的执行请求标识、规范收件 ID、回复 ID 关联；原始
Telegram update 根据账户命名空间、chat ID 和 message ID 关联。未知历史关系不按
正文或时间相近推测。日志与队列没有跨库事务；关联缺失不能伪造执行事实。

## 工作台与 API

工作台新增「收发队列」，支持全部/指定会话、状态筛选、稳定分页、内容和目标、
成功/未知分段、原回执、处置历史，以及执行记录和队列之间双向跳转。

- `transport.list`：session_key、turn_id、status、before、limit。
- `transport.get`：job_id，返回 revision、分段、处置历史和当前允许的操作。
- `transport.review`：job_id、expected_revision、action_id、decision、note、absent_parts。

认证后的远程客户端使用相同 API。核对依据不能为空。旧 revision 拒绝；同一
action_id 的相同请求返回当前结果，不重新排队；复用标识修改请求会拒绝。写审计和
改变队列状态同事务提交。两个客户端竞争只允许一个旧版本请求提交。

## 操作边界

| 情况 | 可执行操作 |
| --- | --- |
| 任务或关联执行仍在运行 | 等待停止后刷新，禁止处置 |
| failed / needs_review | 查看、记录依据并结束处置；满足条件时重新排队 |
| pending 且没有运行中的执行者 | 可结束处置，撤回尚未开始的重试 |
| 已结束处置 | 保留原状态/回执，worker、SDK 队列和直接发送均不得重新执行 |
| 原始 Telegram update | 本阶段只允许查看/结束处置，不重放可能含命令的更新 |
| 规范 Inbox，未接纳执行 | 有稳定执行请求标识且日志可用时，可重新排队 |
| 规范 Inbox，执行已完成 | 可重新排队补建原回复意图，原执行契约保证不再次跑模型 |
| 规范 Inbox，执行已接纳但未完成 | 禁止借队列重跑，转到执行记录核对 |
| 规范 Inbox 身份中的 Bot 与当前账户不同 | 自动消费与人工重试均停止，等待恢复原账户后核对 |
| Outbox，账户改变或渠道未就绪 | 禁止重新排队，不能把旧任务改发到新账户 |
| Outbox，存在未知分段 | 必须逐项核实均未送达；任何不确定或已经送达的未知分段，都不能勾选“未送达” |
| Outbox，部分分段有成功回执 | 重试跳过成功分段，只继续其余分段/保存阶段 |

显式重试给原任务新增最多五次自动尝试额度，保留累计 attempts。成功部分不重置。
未知部分被人工核实后可转为待发送，之前的未知状态和核对依据保存在不可变审计中。
不存在“点击已送达就伪造平台回执”的操作；这种情况可以记录依据并结束处置。

主动提醒适用更严格的 [Phase B 恢复契约](proactive-recovery-v1.md)：未知发送不能靠人工
“未送达”声明重新排队，也不能借历史人工声明获得旧执行续跑资格。已知失败重新排队
后仍须主动恢复入口确认并重新验证资格；通用队列 worker 不绕过这项检查。其他渠道
普通消息的既有人工处置协议保持不变。

结束执行处置不会自动关闭队列，结束某个队列也不会关闭关联的其他任务。申请执行
层面的 `no_effect` 或首次整轮重试时，还检查关联发件：仍可发送的任务或已保存成功
回执的分段会阻止整轮重跑。人工核对的真实性仍由操作者负责，不能承诺外部 exactly-once。

## 验证与后续

回归包括真实子进程在处置事务提交前/后 `os._exit(73)`、重复启动、重复 RPC、分段
成功后超时、账户变化、过期版本、双远程客户端竞争、执行与队列独立关闭和旧库升级。
隐藏离屏 Electron 使用真实 Renderer、preload、RPC 和 Python 后端，核对分段勾选、
重新排队、撤回未执行重试、双向跳转和窄窗口布局。所有网络/模型使用确定性夹具。

后续顺序仍是主动链路事件化、模型上下文投影、受控续跑。本阶段没有实现这些能力，
也没有将独立队列、待办或调度状态迁到统一事件事实源。
