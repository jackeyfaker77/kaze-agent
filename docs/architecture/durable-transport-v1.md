# 持久收件与统一发件队列

后续增量：[收发队列关联查看与人工处置](transport-review-v1.md) 已增加工作台入口、
分段核对、独立关闭和受限重新排队。下文保留持久队列最初阶段的范围记录。

本地 bridge 与独立 Runtime Host 共用 `private_runtime/transport/queue.sqlite3`。
使用 SQLite WAL、FULL synchronous 和工作区内的 OS 排他锁；不新增配置项，
不改变主动提醒的 300 秒周期。队列轮询只做本地 I/O，不调用模型。

## Telegram 入站

SDK 的 update_queue 在 `put(Update)` 返回前保存原始更新，随后 SDK 才推进
getUpdates offset。保存失败会阻止该确认推进，并令渠道健康检查失败。
原始更新按渠道、bot 身份及 update_id 去重；规范消息按 bot、chat_id、message_id
去重。文本、命令、图片和文件均先经过原有权限检查，再进入持久规范收件队列。
重启后恢复原始更新的解析和未执行的规范消息，不依赖 SDK 的内存队列。

规范消息使用稳定 execution_request_id 接入现有执行契约。已经完成的执行可读取
保存的结果，补建缺失的发件记录；已中断或副作用未确认的执行转入待核对，不能
通过重投自动重跑模型或工具。原始更新解析最多尝试五次（含首次），失败后保留记录。

## 出站

普通渠道回复、message_push、主动提醒、调度推送使用同一 Outbox。
发件意图先落盘，再进入原有 ChatLane；附件先复制为持久快照。
普通 Telegram 回复沿用收件身份；定时任务使用 job ID 与本次 fire_at；引用事件的
主动提醒使用目标与事件 ID 集合。其他独立推送生成新身份，调用者也可提供 delivery_id。
同一身份复用不同内容会被拒绝；相同文本的不同合法请求不会被全局去重。
主动提醒的后续 tick 发现同一证据已有发件记录时，会继续原意图；即使模型改写了
措辞，也不会生成第二次推送。投递成功后仍可完成该证据的消费确认。

Telegram 最终文本按平台长度限制分段，文件及图片也分别保存投递状态和 message_id。
成功的部分在后续重试中跳过。渠道账户变化后旧发件进入待核对，不能把旧任务发到新 bot。
其他渠道的 sender 作为一个不可拆分的投递部分，除非适配器明确提供分段持久化能力。

| 状态 | 行为 |
| --- | --- |
| pending | 等待执行或安全重试，重启后继续 |
| running | 正在处理；重启时依据物理发送状态恢复 |
| done | 回执及必要的会话保存完成，重复调用返回保存结果 |
| failed | 永久拒绝或五次尝试耗尽，保留输入和错误类型 |
| needs_review | 物理发送结果未知或账户变化，停止自动发送 |

429 遵从 retry_after；明确的连接建立失败采用指数退避。403、无效请求等永久失败
不重试。读取超时、一般网络错误、发送期间硬退出不能证明平台未收件，因此进入
needs_review，不发送另一个降级通知。已保存回执但会话写入失败时，只补会话保存。
主动及定时消息的 delivery_id 同时用于历史去重，恢复后不会追加第二条相同记录。
补写历史保留提醒依据、来源和规范目标；普通回复的延迟回执只更新原消息。
SQLite 已提交但确认丢失时，重试先核对持久记录，避免再次追加。

恢复 worker 按目标串行，最多同时处理 32 个目标；一个等待重试的目标不阻塞其他目标。
主动提醒另受 [Phase B 受控恢复](proactive-recovery-v1.md) 约束：重启不自动重新发送，
确认后核对原来源和当前资格；Telegram 分片清单先落盘，防止把部分回执当作整条完成。
队列状态计数随 Host 健康状态输出。原始内容和附件属于私有运行数据，备份必须包含它们。

## 范围与限制

- Telegram Bot API 没有这里可用的客户端发送幂等键，不能保证外部平台 exactly-once。
  “平台收件后、本地保存回执前”的空档必须保留待核对，不能同时承诺无丢失和无重复。
- 收件未执行的任务可恢复；已开始的模型／工具执行继续使用现有保守恢复规则。
- Telegram 采用持久最终回复，暂不发送临时推理／工具预览和模拟逐字推送。
  桌面本地与远程的流式事件不受影响，typing 状态仍是临时提示。
- 不自动续跑模型，不引入离线桌面写队列、跨服务器多活或配置迁移。
- 失败和待核对记录不会自动删除或重发；本阶段没有新增人工处置 UI。
  对已删除会话的审计与队列保留策略仍需单独管理。

## 验证

`tests/backend/test_durable_transport.py` 和 `tests/e2e/transport_crash_backend.py`
验证排队、物理发送、回执保存和完成确认边界上的真实硬退出，以及分段重试、附件快照、
身份冲突、账户变更、重试上限、会话保存失败恢复与 SDK 接收落盘失败。

`tests/backend/bootstrap/test_runtime_host_process.py` 使用真实 Host、Telegram SDK、
AgentLoop 和 SQLite，替换模型及 Telegram HTTP 边界，验证收件崩溃、未知发送、
回执保存后崩溃、429 重试与重复 update 在重启后只产生一次模型执行和一次平台消息。
本地桌面与远程 Calendar MCP 流程另行运行既有端到端探针。
