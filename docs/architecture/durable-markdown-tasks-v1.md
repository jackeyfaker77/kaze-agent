# Markdown 历史归档与近期摘要持久恢复 v1

本轮在原可靠基础版 `3f421c5` 上补齐 Markdown 归档链；独立于 Akasha 和服务器部署。PR #33 已合并、CI 通过并加载生产，纳入当前 `2ade483` 基础版；原基线的历史验收范围不追溯扩大。自动化与生产验证边界见文末。

## 所有权与入口

- Runtime Event Log 中已提交的 `conversation.changed` 携带 `markdown_maintenance` 意图，关联原执行、会话与渠道。唤醒只是提示；进程重启扫描事实即可补入队列。
- `memory/markdown_tasks.sqlite3` 拥有发现游标、任务领取、不可变处理快照、归档草稿及文件写入回执。入队与扫描游标同事务，原执行身份唯一去重。
- 已记录模型请求和结果仍由执行日志拥有。Markdown 任务复用同一持久模型步骤协议，不在任务库维护第二份模型结果。
- HISTORY、PENDING、RECENT_CONTEXT 和日记是 Markdown 领域文件。本轮不将所有手工编辑或画像操作改为事件溯源。
- 会话归档进度仍属于会话事实；只更新进度，不把后台的旧会话快照整份写回，避免覆盖前台新增消息。
- 默认 memory2 的归档后回调交接给已有持久记忆任务队列，关联 Markdown 任务 ID。Markdown 文件完成和回调完成是两个独立状态；`memory.tasks.list` 返回原有 `tasks` 和新增的 `markdown_tasks`，本地及远程共用入口。

## 固定输入与模型恢复

领取后保存已提交会话窗口、原进度、渠道、keep_count、模型名称以及当时的长期画像、历史参考和近期摘要。先持久化快照再调用模型。

归档抽取与近期压缩使用稳定步骤身份。恢复查到已提交模型结果时直接复用；请求可能发出但结果未落盘时标记 blocked，不自动重试。没有出站尝试记录的中断可重新领取新一代模型执行。模型成功返回后的解析失败也保持可见，不能偷偷调用模型修补 JSON。

草稿保存之后不再调用任何归档／摘要模型。近期对话尾部刷新无需模型，也走持久任务和文件写入协议。

## 文件与跨存储恢复规则

每个文件操作先提交原内容 SHA-256、目标完整字节和任务身份，再写同目录临时文件、flush/fsync、原子替换。恢复时：

| 持久证据 | 行为 |
|---|---|
| 文件还是原内容 | 写入已保存的目标内容 |
| 文件已等于目标内容、回执未提交 | 只补回执，不追加 |
| 写入回执已完成 | 跳过，不把之后的用户编辑或 PENDING 消费恢复成旧内容 |
| 文件既非原内容也非目标内容 | blocked，保留外部更改，不盲目覆盖 |

文件完成后提交会话进度；再用稳定任务身份交接 memory2 回调，最后完成 Markdown 任务。任一进程崩溃窗口可重新打开数据库恢复。memory2 回调的检索、模型、记忆写入均复用持久步骤；向量、事件记录和步骤回执处于同一事务边界。回调异常不能被吞掉并标成成功。

同一工作区所有会话共用 Markdown 文件，因此按持久入队顺序处理。旧任务未知或发生文件冲突时阻塞后续 Markdown 工作，防止旧摘要覆盖新摘要；前台对话和独立的回复后记忆队列继续运行。正在存活的执行 epoch 不可被另一个工作者抢占。

## 兼容与限制

- 旧历史继续可读，按已有 last_consolidated 接续；没有新意图的旧事实不被批量补算，避免升级触发大量模型调用。新对话或显式归档请求会处理符合窗口条件的旧历史。
- 手动归档也走同一队列，以原会话消息内容和请求类型去重；重复点击不产生第二份模型调用和文件写入。
- 已删除／修改的来源会话在处理前及模型返回后重新检查；不重建被删除的会话来完成旧任务。
- 保留普通本地／远程运行、原模型配置及 wake 的 300 秒轮询。每秒后台扫描只读本地队列，不代表每秒调用模型。
- 未知外部模型／embedding 结果继续阻塞。本轮不提供通用未知结果核验，也不保证服务端 exactly-once。
- 进程崩溃证明不等同于断电或不受约束的外部文件写入者并发证明。发现文件冲突时停止；不要自动清除任务库来“重试”。
- 只接通当前默认 memory2 的可靠回调，不切换或承诺 Akasha 的学习恢复。不支持任意自定义 after_consolidation hook 的自动重放。
- 冷备份工具会一并包含新任务库及 WAL 已提交数据；旧备份恢复仍保持隔离，不能自动重新上线。

- 本地／远程生产入口复用 `tests/backend/memory2/test_memory_tasks_host.py` 验证正常提交及保存失败后的补存都能发现任务。

## 本机最终验收（2026-10-28）

平台：Windows、Python 3.12.13。所有故障注入均使用临时工作区，不修改生产配置；真实调用计数采用正式 Provider 投影路径和可计数的 HTTP 替身，不等同于本轮真实 Telegram／在线模型验收。

- 最终 Markdown 专项：**36 passed**，启用 `-W error`。其中 27 个真实子进程退出边界，各重新开库恢复两次；另 9 项覆盖并发、旧历史、手工编辑冲突及回调。每日 journal 写入边界与 Host 就绪探测追加复核各 1 passed。
- 正常归档与摘要总共调用模型 2 次；启用默认引擎归档回调后共 3 次。结果已提交后的恢复不增加调用；未知第一步／第二步／回调调用分别停在 1／2／3 次，任务保留 blocked。
- HISTORY、PENDING、RECENT_CONTEXT 和每日 journal 的输出各一次，进度恢复正确。完成写入后已被消费的 PENDING 不会重新追加；摘要在模型调用期间被手工修改则保留修改并阻塞。
- 扩展记忆、运行时、远程入口及受控续跑集成：**275 passed**。
- 另跑 bootstrap、desktop_bridge、agent/core、内部模块与 session：首轮 363 passed、2 skipped、2 failed。两处失败分别为新增依赖未加入单元测试替身，以及测试的就绪探测短暂抢占 Host 启动锁；均修正测试夹具，未削弱生产锁。受影响的完整 Host 进程与 wiring 文件复测 **33 passed、1 skipped**。Windows 不适用的 SIGTERM 与符号链接权限项不计为通过。
