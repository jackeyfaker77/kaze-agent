# MCP 连接自动恢复

范围：Calendar、Feed 等现有 stdio MCP 的连接生命周期；本地内嵌与独立 Runtime Host 共用同一实现。业务配置和主动轮询 300 秒不变。

## 故障与处理

旧注册表只在启动时连接一次。Windows 登录初期依赖启动失败后，Host 和 Telegram 可以正常工作，但 MCP 工具长期缺失。旧保存逻辑还会仅保存在线客户端，导致操作其他服务时丢失离线服务配置。

- 配置记录独立于在线连接。恢复使用原 command、env、cwd，不调用 `mcp_add`、不保存配置；添加其他服务也保留离线记录。
- 每个服务只有一个连接恢复任务和连接锁；失败后从 2 秒指数退避到 60 秒。健康连接每秒仅检查本地进程状态，不调用模型或远端工具。
- 连接超时或取消会清理子进程；传输断开、工具等待超时或取消将连接标记为不可复用，随后重新握手、获取工具目录。删除、禁用或关闭后停止恢复并移除工具。
- **连接恢复绝不重发 `tools/call`。** 已派发但未确认的结果保持未知；新连接可用不代表旧业务执行获得重试许可。结构化工具错误也不伪装成成功。
- Host 健康信息增加 `mcp_health` 和 `dependencies_ready`，与主服务存活分开报告。主动轮询先检查旧执行阻塞，再检查本轮声明的主动来源 MCP 就绪；无关可选 MCP 离线不阻塞提醒。依赖未齐时不接纳新主动执行、不调用模型或工具。下一次正常轮询再判断。

## 回归证据

`tests/backend/test_mcp_recovery.py` 覆盖冷启动失败后恢复、配置字节不变、连接替换、并发添加、保留离线配置、移除／禁用／关闭停止恢复、离线工作目录冲突，以及连接重置／超时／取消不重发工具。

真实 stdio 子进程测试先让初始化超时，再连接成功；工具请求收到后子进程强制退出，连接恢复后原请求计数仍为 1。隔离测试不连接生产 Telegram。

`tests/backend/bootstrap/test_proactive.py` 验证依赖离线时没有新执行、模型、来源调用或发送，恢复后正常发送及 ACK 一次，后续轮询不重复。既有主动恢复矩阵继续验证未知结果阻塞和崩溃恢复。

## 2026-10-30 旧执行处置

旧主动执行停在 Calendar 候选读取阶段；原日志有 3 次工具派发及返回，没有模型请求、发送、ACK 或关联发件任务。Calendar 候选读取会记录候选版本，不能据此认定没有副作用。

只读核对后，用户明确授权通过 `execution.review` 关闭／放弃该执行。仅追加人工关闭事实，原未知回执保留，不授予重试许可、不重跑旧工具。后续主动提醒是新的执行。

边界：进程存活不等于远端业务可用；尚未发起请求的挂起进程不会由本地存活检查识别。网络发送结果未知仍需核对，不承诺外部系统 exactly-once。
